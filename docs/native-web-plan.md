# Unlight 原生 Web 移植規格與雲端交接

從 `codex/unlight-native-web` 接手。先跑[基準檢查](#基準檢查)，再開工 [NW-01](#nw-01-原生-web-入口)。本計畫承接[現代化計畫](../MODERNIZATION_PLAN.md)，本頁記錄目前的程式基準、切片順序和完成條件。

## 起點

- `16f27aa` 包含繁中 Flash／Ruby 的建置、驗收方式和獨立的[《霧潮航線》技術試驗](../modern/README.md)。該試驗可參考 Rust／Wasm、Axum 和瀏覽器回放接法。
- `990292e` 把 [ActionScript 封包格式](../app/client/src/net/ULSocket.as)移植到[原生 JavaScript](../tools/legacy-web/protocol.mjs)。Mac 的四項 Node 測試已通過，Chrome 停用 Ruffle 時也收到六項 Ruby 服務的 KeepAlive。相容頁的標題與音訊回歸通過。登入、遊戲畫面與 Rust 戰鬥核心屬於後續工作。
- Ruby 的[固定對局 `2026`](../tools/legacy-server/fixtures/trace-2026.json)包含 `seed`、`outcome` 和 `trace`，共 68 筆事件。它是目前可重跑的行為基準。[Ruby 啟動和驗證方式](../tools/legacy-server/README.md)

## Spec 範圍

第一個可玩里程碑是**用原生瀏覽器完成一場現有的單人 PvE 測試流程**。驗收自隔離帳號登入開始，經由大廳、選擇測試任務、出牌、結束回合、AI 回合，直到結算與回到大廳。流程涵蓋正體中文操作文字、基本鍵盤操作、連線中斷提示、可重試的操作和結算寫入。瀏覽器驗收會封鎖 SWF 和 Ruffle 的網路請求。

| 里程碑 | 執行方式 | 完成條件 |
| --- | --- | --- |
| M1 原生 Web 試玩 | TypeScript／HTML 透過相容層接現有 Ruby 服務，使用隔離測試資料 | 瀏覽器可從登入走到一場 PvE 結算，重讀後可查到一次且僅一次的結算結果 |
| M2 Rust 核心與 Wasm 回放 | 由同一份 Rust 核心處理原生回放與瀏覽器回放，使用固定狀態、操作、亂數和時鐘輸入 | Ruby、原生 Rust 和 Wasm 的已驗收事件順序、結果及狀態欄位一致 |
| M3 現代後端 | Axum 提供測試對局的 HTTP／WebSocket，Rust 管理權威狀態，SQLite 保存測試進度 | 獨立啟動現代應用即可跑完 M1 的主流程，並通過權限、重送、重連及重啟驗收 |
| 後續功能 | 盤點既有程式的牌組管理、角色成長、任務與 PvP，按使用者流程補測例、實作及驗收 | 每項都在覆蓋表對應來源路徑、測例、已知差異和實機結果 |

第一個里程碑使用隔離開發帳號和資料庫。正式帳戶遷移與正式上線各自立票。畫面採可操作的現代 Web 介面，素材採已有可用權限的檔案或原創測試素材。程式碼遵循[倉庫授權](../LICENSE)，素材依[既有來源清單](../tools/legacy-build/README.md)分別核對。

### 模組介面

| 模組 | 呼叫方式與責任 |
| --- | --- |
| 瀏覽器通訊 | 沿用 `relayURL`、`encodeClientFrame` 和 `ServerFrameDecoder`。相容介面管理連線與逾時，畫面接收結構化的連線狀態和資料。 |
| 登入與資料 | 先以現有 Ruby 行為為準，對畫面提供登入、登出和玩家快照。把舊協定或會話狀態留在相容層內。測試使用獨立帳號，憑證透過執行環境注入。 |
| 對局 | 輸入初始狀態、經驗證的操作與明確的亂數／時間值，回傳新狀態和有序事件。Rust 原生執行與 Wasm 共用邏輯。 |
| 主機與呈現 | 伺服器以玩家視角輸出可見狀態和事件，瀏覽器依資料呈現與播放動畫。網路、資料庫和動畫各自透過模組介面測試。 |

### NW-00 — 原生封包

完成依據為 `990292e`。Node 測試涵蓋同來源的 `ws`／`wss` URL、雙位元組長度和結尾、拆開或合併的回應、內嵌換行，以及無效長度與結尾。瀏覽器以 `WebSocket` 連現有相容層並驗證六項服務的回應。

### NW-01 原生 Web 入口

建立 `native-web/` 的最小 TypeScript 網頁和可重跑的建置、啟動指令。使用現有封包模組，從同來源建立一條實際的 Auth WebSocket 請求並回報連線狀態。沿用[相容試玩入口](../tools/legacy-web/README.md)作為回歸基準。

**單元測試**覆蓋連線狀態 `idle` → `connecting` → `ready`、逾時、斷線、重試，以及過期連線的事件對當前畫面的影響。以可控制的 WebSocket 連線與時鐘測試狀態。

**完成條件**是全新 checkout 可建置並啟動，真實瀏覽器在 SWF 與 Ruffle 請求被封鎖時仍能收到 Auth 回應。提交可重跑的指令和瀏覽器檢查。

### NW-02 — 登入與會話

依[登入指令](../app/client/src/net/command/AuthCommand.as)及[ActionScript 登入流程](../app/client/src/net/server/AuthServer.as)整理相容介面。打通隔離帳號登入、登出、失敗處理和連線中斷後回到可操作狀態。沿用現有流程中的挑戰與回應，讓會話資料留在受控的執行環境裡。

**單元測試**覆蓋 UTF-8 欄位的長度與編碼、截斷回應、失敗代碼、逾時、過期回覆、登出清理。**整合驗收**需用隔離的真實 Ruby 認證服務測成功與錯誤密碼，檢查測試輸出與前端持久化儲存中的憑證處理。

### NW-03 — 玩家資料與大廳

用經過篩選的登入後玩家快照填充大廳與最小任務選單。任務項目直接關聯固定測試資料 ID。

**單元測試**覆蓋初始化、空資料、更新舊資料、無權限的快照和重複事件。**完成條件**是新登入可選定測試任務，重整或斷線後可回到一致的玩家狀態。瀏覽器以鍵盤操作走過同一流程。

### NW-04 — 可重播的 PvE 測例

先讓 Ruby 的 68 筆既有事件重跑通過。沿用[對局驗證器](../tools/legacy-server/duel.rb)，把一場測試對局的初始資料、合法操作、亂數和時間依序記錄成可獨立餵入新實作的資料。比對保留事件順序、實際數值、雙方 HP 和結算。

**單元測試**覆蓋測例載入、事件順序與數值差異、非法操作、重複輸入、缺少亂數或時間值。**完成條件**是相同輸入重跑兩次輸出一致，修改一筆有意義的狀態或事件後能指出第一筆差異。若基準含時間戳或執行期識別碼，逐欄記錄可正規化的理由。

### NW-05 — 原生瀏覽器 PvE

以現有 Ruby 為權威，接上原生頁面的回合操作、事件呈現、結算和返回大廳。

**單元測試**覆蓋可用操作、事件去重、動作提交失敗後的重試、結算狀態同步。**完成條件**是 Playwright 使用測試帳號走完 M1，記錄結算與重讀後的結果，並保存一次開局、對局和結算的實機畫面。

### NW-06 — Rust 核心與 Wasm

依 NW-04 測例一次移植一段規則。參考現有 Rust／Wasm 的建置方式，把對局和輸出事件置於可獨立重播的 Rust 模組。

**單元測試**覆蓋牌堆耗盡、移動上下限、回合切換、擲骰與傷害邊界、技能觸發順序、合法與非法操作、勝敗和結算。**完成條件**是固定測例的有序事件及狀態比對在原生 Rust 和瀏覽器 Wasm 都通過。

### NW-07 — Axum 對局服務

以 NW-06 的 Rust 模組提供開局、玩家快照、送出操作與 WebSocket 狀態更新。HTTP 初始化使用同一份可見狀態，後續事件附帶可核對的版本。

**單元測試**覆蓋角色視角的狀態投影、操作權限、重複提交和版本不符。**整合驗收**需驗證兩個連線的可見狀態、重送一次操作的效果，以及頁面真的接到伺服器推送。

### NW-08 — 結算保存與獨立啟動

在 SQLite 交易內保存測試對局結果和玩家進度。重連由最後確認的版本恢復可見狀態。整理單一的現代版啟動入口。

**單元測試**覆蓋版本恢復、結算重送和讀取舊資料時的預設值。**整合驗收**需模擬寫入途中失敗、重複結算、斷線重連及重啟載入。以只啟動現代應用的環境重跑 M1，驗證全流程和資料保存，記錄載入時間與操作延遲。

### NW-09 — 後續功能盤點

逐個核對既有程式的牌組、角色成長、任務及 PvP 入口，為每項寫明可執行操作、資料依賴、單元與整合測例、優先序及驗收條件。**完成條件**是每個納入的使用者流程均可對照到來源、測例和實機結果，未知項有明確的待確認記錄。

## 開發方法

1. 一次完成一張任務票。從對應的原始碼入口和已測行為寫驗收條件，固定輸入資料並記錄基準輸出。
2. 先寫一個會因缺少目標行為而失敗的測試，再實作最小切片，最後整理重複邏輯。單元測試從公開介面送入操作並檢查狀態、事件或明確錯誤。透過介面傳入參數或依賴，讓測試能控制時間、亂數、WebSocket 和資料庫。
3. 先跑純 Node 或 Rust 測試，再以隔離服務驗證協定及資料，最後從真實瀏覽器完整走一次任務票所涉及的操作。用現有 Ruby 測例核對相同行為，記錄第一筆有意義的差異。
4. 提交記錄包括任務 ID、驗收摘要、可重跑指令及已知差異。程式與對應測試一起提交。測試帳號、資料庫、生成資產和機器專用路徑留在執行環境。
5. 只有通過該票的完成條件才更新狀態。瀏覽器端的切片同時記錄實機操作結果，供下一個 session 重跑和核對。

## 基準檢查

從倉庫根目錄先驗證已提交的封包實作。

```sh
node --test tools/legacy-web/protocol.test.mjs
```

依[舊版 Ruby 啟動說明](../tools/legacy-server/README.md)裝好鎖定的相依套件後，重播固定對局。

```sh
BUNDLE_GEMFILE="$PWD/tools/legacy-build/Gemfile" \
  bundle exec python3 tools/legacy-server/run.py characterize --check
```

已有雲端試玩服務時，先以 HTTP 確認實際埠號。需要重建時沿用[繁中客戶端建置](../tools/legacy-build/README.md)與 [Ruffle Web 啟動說明](../tools/legacy-web/README.md)，再把實際埠號和 Chromium 執行檔路徑傳給驗證程式。

```sh
python3 tools/legacy-web/check_boot.py "$UNLIGHT_BASELINE_PORT"
python3 tools/legacy-web/check_relay.py "$UNLIGHT_BASELINE_PORT"
python3 tools/legacy-web/check_browser.py \
  --port "$UNLIGHT_BASELINE_PORT" --chromium "$UNLIGHT_CHROMIUM"
```

`check_browser.py` 會先封鎖 Ruffle 並驗證原生 WebSocket，再走相容頁的標題、音訊和 WebGL 2 失敗重試。雲端 Chromium 需要軟體 WebGL 時可依原說明加上 `--software`。以雲端當前工作區的實際連線和預覽設定為準。
